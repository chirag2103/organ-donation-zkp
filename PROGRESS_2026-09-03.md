## 4. Live Hands-On Testing Session — bugs found and fixed while actually using the app

This was the largest and most consequential session: testing the running app surfaced several real, previously-undetected bugs in areas the automated test suite didn't cover (frontend logic, cryptographic parameter tuning, missing features).

### 4.1 Merkle tree build — ~1–3 minutes on every login, fixed to ~5ms

**Root cause:** `buildMerkleTree()` (in `server/zkpService.js`, plus 3 duplicated copies in `scripts/benchmark.js` and two integration test files) built the full 20-level tree by hashing all 2²⁰ (~1,048,575) leaves pairwise from scratch — even though only 1 leaf (the credential) is ever non-zero.

**Fix:** precompute the "zero-subtree hash" at each level once (independent of credential — only 20 Poseidon calls, ever), then walk the credential's path directly using those cached constants (20 more calls). This is the standard "cached zero-value incremental Merkle tree" technique (used by Tornado Cash, Semaphore, etc.).

**Verification:** proved mathematically identical output (root + path) to the old algorithm across multiple credentials and depths *before* touching production code, then applied to all 4 duplicated copies. Full test suite (including real Groth16 proof generation) dropped from ~4 minutes to ~5–7 seconds.

### 4.2 IPFS-backed compatibility scoring was never actually using real data

**Root cause:** `CompatibilityScore.jsx` fetched `OrganRegistry.getCompatibilityScore()` but never decoded/used the result — it always scored hardcoded placeholder strings (`'DEMO_D_BLOOD'`, etc.), which would fail SEAL's ciphertext deserialization if ever actually reached. Separately, donor/recipient registration wrapped the real BFV ciphertexts in an AES-256-GCM layer keyed to the *specific, ephemeral, 4-hour* `PFEKeyIssuer` session that registered them — meaning a different role/session (e.g. a Surgeon viewing a Doctor-registered donor) could never decrypt it, even in principle.

**Fix:**
- Donor/recipient registration now uploads the raw BFV ciphertext JSON bundle directly to IPFS (still never plaintext — confidentiality comes from the SEAL encryption itself, not a redundant, cross-session-incompatible AES wrap). Access control is the existing on-chain `onlyValidKey` + `hasPermission` gate on `getCompatibilityScore`, consistent with the rest of the system's design.
- New backend endpoint `GET /api/ipfs/download/:cid` + frontend `downloadFromIPFS()` to fetch it.
- `CompatibilityScore.jsx` now actually decodes the on-chain response and scores the real fetched ciphertexts.

**Verified** via a scripted end-to-end pipeline test (encrypt → raw upload → download via new endpoint → homomorphic score → decrypt) against the live IPFS daemon and backend — full round-trip correct.

### 4.3 Bonus fix found in the same investigation: IPFS status check was a false negative

`ipfsService.checkIPFS()` called `.id()`, which throws on this Kubo daemon version (`no protocol with name: webrtc-direct` — a `multiaddr` parser incompatibility with newer Kubo). This made `/api/status` report `ipfs:false` even when uploads/downloads worked perfectly. Switched to `.version()`, which avoids multiaddr parsing entirely. Confirmed `/api/status` now correctly reports `ipfs:true`.

### 4.4 Recipient Registration UI was completely missing

The "Register" tab only ever rendered `DonorRegister.jsx` — there was no way, anywhere in the UI, to register a recipient, despite `OrganRegistry.registerRecipient()` being fully implemented and tested at the contract level. Added `RecipientRegister.jsx` (mirrors donor registration, calls `registerRecipient(encCID, bloodType, hlaRoot, urgency)`) and `RegisterPanel.jsx` (a Donor/Recipient toggle now rendered by the Register tab).

### 4.5 "Find Best Matches" auto-matching feature (new capability, not a bug fix)

Previously, matching was purely manual (type a donor ID and a recipient ID, look up one pair). Added a "🔍 Find Best Matches" view that reads `donorCount()`/`recipientCount()`, loads every *active* donor's/recipient's real ciphertexts once each (avoiding redundant IPFS downloads), scores every pair homomorphically, and shows a ranked table with the best match highlighted — built on top of the real-data fix in §4.2.

### 4.6 Compatibility score labels were inverted (found via live testing — user noticed a "perfect" 0-distance pair labeled "Poor match")

**Root cause:** `computeCompatibilityScore()`'s formula is a *dissimilarity distance* (0 = identical/perfect, larger = more different — this is deliberate and matches an already-passing test asserting "should return 0 for a perfect match"). But `interpretScore()` treated the raw number as if higher = better compatibility — so a perfect match (0) was labeled "Poor match," and "Find Best Matches" was sorting the *worst* pairs to the top.

**Fix:** added `toCompatibilityScore()` (`1000 − distance`, clamped) in `src/utils/pfe.js`, applied at the display/ranking layer only — deliberately did *not* change `pfeService.js`'s core functions, since existing tests assert specific raw distance values that are still correct as distances.

### 4.7 Blood-type matching wasn't doing real ABO/Rh compatibility, and HLA differences were nearly invisible to the score (found via live testing — user noticed identical HLA scores still showing "poor match", and a 2%-vs-70% HLA gap scoring "perfect")

This was the deepest fix of the session, touching the actual homomorphic encryption scheme.

**Bug 1 — blood type reduced to one bit.** Before encryption, `bloodType > 0 ? 1 : 0` collapsed every blood type except A+ to the same value "1" — so B+, O-, AB+, everything, were indistinguishable to the scoring formula. Not real ABO/Rh compatibility at all.

**Bug 2 — HLA differences rounded away to nothing.** The final descaling step divided by `SCALE²`, which exactly cancels any `SCALE` increase — the HLA term mathematically reduced to `round(diff²)`, and since `diff² ∈ [0,1]`, it could only ever round to 0 or 1, regardless of how fine the input quantization was. Meanwhile a full blood "mismatch" (per the crude bit above) always cost exactly 100 points. Net effect: blood dominated almost entirely, HLA barely mattered, and two different-but-real-life-incompatible blood types (e.g. B+ and O-) that both collapsed to "1" could score a "perfect" 1000/1000 despite wildly different HLA.

**Fix (verified against a plaintext reference before touching production code):**
- Decompose blood type index (0–7) into `(isA, isB, isRhPos)` before encryption — 5 ciphertexts per record now (`ctIsA, ctIsB, ctIsRhPos, ctHla, ctUrgency`) instead of 3.
- Compute real donor→recipient ABO/Rh incompatibility homomorphically: for each antigen, `donorHasIt AND NOT recipientHasIt` (one multiplication each, 3 independent single-level multiplications summed — same multiplicative depth as the original scheme, so no crypto-parameter changes needed).
- Added an explicit `HLA_WEIGHT` constant (like blood already had `W`) so HLA differences actually move the score, instead of being silently absorbed by the final descale.
- Widened `SCALE` from 10 to 20 for finer input quantization (5% HLA granularity), staying safely within the *existing, unchanged* BFV plaintext modulus (verified empirically: 5/5 repeated stress-test runs across all 64 blood-type-pair × multiple-HLA combinations, all matching a plaintext reference exactly).

**Verified with the user's own reported scenarios, recomputed correctly:**
| Scenario | Before | After |
|---|---|---|
| O- donor (2% HLA) → A+ recipient (70% HLA) | 900/1000 ("perfect"-ish, HLA ignored) | ~853/1000 — correctly reflects real compatibility (O- is universal donor) *and* the HLA gap |
| B+ donor (2% HLA) → O- recipient (70% HLA) | 1000/1000 ("perfect" — wrong; both blood types collapsed to the same bit) | ~653/1000 — correctly reflects real incompatibility (B+ can't give to O-) *and* the HLA gap |

Updated 5 PFE integration tests with hand-verified expected values for real blood-type scenarios (perfect match, universal donor, worst-case 3-antigen incompatibility, the previously-broken same-bit-collapse case). All 62 fast tests pass.

### 4.8 Diagnosed (not a bug): MetaMask nonce desync after chain restarts

Multiple "transaction failed" reports traced to MetaMask's cached nonce going stale every time the Hardhat node restarts (the in-memory chain resets to nonce 0, but MetaMask remembers the account's prior nonce from before the restart). Not a code issue — documented the fix (MetaMask → Settings → Advanced → "Clear activity and nonce data") and baked a reminder into `start-all.ps1`'s output.

### 4.9 Diagnosed (not a bug): stale `deployments.json` after node restarts

Reproduced and explained the `could not decode result data (value="0x")` error pattern — happens whenever the Hardhat node restarts (wiping all deployed contract state) without re-running `deploy.js`, since `deployments/localhost.json` still points at addresses with no bytecode on the new chain. `start-all.ps1`'s sequencing (§3.2) prevents this going forward.
